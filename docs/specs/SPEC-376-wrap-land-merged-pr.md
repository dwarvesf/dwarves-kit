# Spec: wrap land recognizes an already-merged own PR before opening a new one
Generated: 2026-09-30
Status: VALIDATED
Lane: full
Depth: blind-spot (failure: a branch re-pushed with new commits after its own PR already merged must still open a fresh PR for those new commits; a detection rule that only checks "does gh already call this PR MERGED" could wrongly treat the whole branch as landed and silently drop the new commits. Two review rounds have since found five more blind spots in earlier drafts -- a lock-destroying reorder, an unleased origin-branch delete, a missing origin-freshness check, a silently-closed coexisting PR, and a freshness check that failed OPEN on a network error -- which is why this depth held rather than getting downgraded)
References: `lib/wrap/wrap-apply.sh:6-26` (`_merge_proof`, the ancestor/absorbed/squash proof `wrap apply`'s worktree tidy already trusts for "this branch is already merged, tidy it"); `lib/wrap/wrap-carry.sh:74-90` (`_autoland_carry`, the one other caller that checks a squash proof AND an origin-freshness `ls-remote` before deciding to open a PR at all -- both patterns this spec reuses, and REFUSES on that `ls-remote` coming back empty, the exact fail-closed behavior this spec's own freshness check now matches); `lib/wrap/wrap-apply.sh:104-197` (`_apply_worktrees`, the fetch-then-proof-then-recheck-then-remove sequence this spec mirrors for `cmd_land`, including WHERE the recheck sits relative to the actual removal); `docs/verification/wrap-land.md:3` (the documented refusal list, including "no commits ahead of the default branch," that this spec keeps unchanged).

## Problem

On 2026-09-30, in a consumer repo adopted into this operate-contract, PR A on a feature branch was squash-merged. `bin/wrap land <worktree>` then ran on the same worktree, which still held the pre-merge commits. It:

1. Pushed the stale worktree copy of the feature branch to origin (harmless by itself -- the branch ref, not the default branch).
2. Looked up open PRs for that branch, found none (PR A is `MERGED`, not `OPEN`), and fell through to `gh pr create`.
3. Opened PR B with a diff byte-identical to PR A's already-landed content, then squash-merged PR B too.

Expected: land notices the branch's own PR already merged (or that the branch's content is already on the default branch by another proven route), stops without pushing or opening anything, and tidies the worktree the same way a normal post-merge land does. The adopt path (an already-OPEN own PR for the branch) is unaffected and must keep working exactly as it does today. Two rounds of validation (7 parallel reviewers each) have found and closed real defects in this design; see `## Design` and `## Decision Log` for the shape both rounds settled on.

## Root cause

`cmd_land` (`lib/wrap/wrap-land.sh:75` onward; all bare `:N` citations below are `lib/wrap/wrap-land.sh` line numbers before this spec's build, unless a file is named) has no step that asks "has this branch's content already landed?" before deciding to push and open a PR. Two things hide the fact from it:

- The `ahead` check (`lib/wrap/wrap-land.sh:126`, `git rev-list --count origin/<def>..<branch>`) is pure commit-graph ancestry. A squash merge writes a brand-new commit on the default branch with a new SHA; none of the original branch's commits become ancestors of it. So `ahead` stays greater than zero forever after a squash merge, and land reads that as "real, unlanded work."
- The open-PR lookup (`lib/wrap/wrap-land.sh:149-161`, `gh pr list --head <branch> --state open ...`) filters `--state open` only. A `MERGED` PR for the same head is invisible to it.

**The exact decision point is `lib/wrap/wrap-land.sh:191-207`**, the `else` arm of the `open_count` cascade (`open_count -gt 1` refuse / `-eq 1` adopt / else create):

```
2521    else
2522      # `--head`, never `--base`: ...
2523      if [ -n "$body_file" ]; then
2524        created="$(gh pr create --repo "$url" --head "$branch" --title "$title" --body-file "$body_file" 2>&1)"; rc=$?
...
2536      echo "     opened PR #${n}"
```

`open_count` is 0 whenever there is no *open* PR for the branch -- which is exactly the state a branch is in the moment its own PR merges. Nothing between the fetch (line 2455) and this `else` ever asks whether the branch is already proven merged, so a just-merged branch and a genuinely brand-new branch look identical to this code, and both fall into the same "create a PR" arm.

`wrap.sh` already has the check land is missing: `_merge_proof` (`lib/wrap/wrap-apply.sh:6-26`) answers "has this branch already reached the default branch," across three routes -- a plain ancestor, tree-identical content absorbed without a matching PR (`_absorbed`), or a gh-recorded squash merge (`_squash_json` / `_squash_verdict`, the same helper `_autoland_carry` already checks at `:86-90` before it will open a PR). `wrap apply`'s worktree-tidy pass (`lib/wrap/wrap-apply.sh:146-148`) already calls `_merge_proof "$repo" "$def" "$ghs" "$wtb"` before removing a worktree and deleting its branch. `cmd_land` is the one caller that reaches the same "should I open a PR / should I tidy this worktree" fork without ever asking that helper.

**A mathematical fact that shapes where this check may run, and what it depends on:** `ahead` (line 2456) and `_merge_proof`'s ANCESTOR route (`lib/wrap/wrap-apply.sh:15`, `merge-base --is-ancestor refs/heads/<b> refs/remotes/origin/<def>`, using FULL refs per the tag-shadow warning at `:12-14`) are mutually exclusive, PROVIDED both sides resolve the same objects. If the branch tip is an ancestor of `origin/<def>`, then every commit reachable from the branch is already reachable from `origin/<def>`, so `origin/<def>..<branch>` (what `ahead` counts) is empty and `ahead` is 0. But `ahead`'s own command today uses SHORT names (`origin/${def}..${branch}`), while `_merge_proof`'s ancestor check uses full refs -- exactly the shadowing `_merge_proof`'s own comment warns against (a tag or local branch sharing either name resolves first for a short name and not for a full ref). If a repo carries such a shadow, `ahead` and the ancestor check could silently disagree, which would reopen this fact's guarantee in a narrow case. This spec closes that gap by moving `ahead`'s command to full refs too (`## Design`, Decision 1; `## Task Breakdown`, TASK-1), so both sides resolve the same objects, restoring the guarantee; a second, cheap guard (Decision 1) also refuses to act on an ancestor-shaped proof at this call site regardless, so a hole in this reasoning stays inert rather than dangerous. Once the guarantee holds, `cmd_land` already refuses outright at `ahead == 0` (`:128-129`, documented at `docs/verification/wrap-land.md:3`) before this spec's new check ever runs, so **the ancestor route cannot fire from this call site in practice**: only the absorbed and gh-squash routes are reachable once the check is gated behind `ahead > 0`. This also means a brand-new, zero-commit `wrap start` worktree -- trivially an ancestor of `origin/<def>` -- never reaches the new code at all; it still refuses at `ahead == 0` exactly as today.

## Solution

### Approaches considered

| # | Approach | Tradeoff |
|---|---|---|
| A | Widen the open-PR lookup to `--state all` and special-case a `MERGED` result | Catches the squash-merged-PR case only; still blind to content absorbed without a matching PR (e.g. a subagent branch a lead re-committed under its own PR), and re-derives a check `_merge_proof` already gets right |
| B | Call `_merge_proof` after the existing `ahead > 0` gate; a proof found (guarded, see `## Design`) skips to a shared tidy tail; no proof falls through to today's push/PR/merge path, which now ends at the same tidy tail | One extra call to a helper this file already trusts for the identical question, plus the guards `_apply_worktrees` and `_autoland_carry` already carry for exactly this kind of check (fetch-rc, a dirty/tip recheck positioned right before the destructive removal, an origin-freshness read that fails CLOSED) |
| C | A narrower, gh-only check: call `_squash_json`/`_squash_verdict` directly against the local tip, skipping `_merge_proof`'s ancestor and absorbed routes entirely | Smaller diff and no dependency on `_absorbed`'s tree walk, but blind to the absorbed-content route entirely (a branch whose net change landed without ever having its own merged PR, e.g. a re-committed subagent branch, or `wrap merge`'s `<branch>-squash` fallback that leaves the original PR open -- commands/wrap.md:116). It still needs the same post-round-trip guards B does, since it still makes a network call, so it saves no guard code, only the one extra `_absorbed` tree walk. Rejected: it trades real coverage for a saving that does not materialize |

### Chosen approach + why

B. `_merge_proof` already owns the enumeration of "how a branch's content can already be on the default branch" and is exercised in production by two other callers; land reusing it, gated behind the pre-existing `ahead > 0` refusal and wrapped in the same guards those callers already carry, is the only approach that closes the absorbed and gh-squash cases at once without opening the lock-destruction risk round 1 found in a naive "check before the ahead gate" ordering, and without inventing new proof logic a second way (C's narrower rewrite would still need every guard B needs, for strictly less coverage).

### Extensibility & boundaries

- Load-bearing dimension: the set of ways a branch's content can already be on the default branch. `_merge_proof` already owns that enumeration; this spec adds no fourth way, and reachable here it is really only two of the three (ancestor is excluded by construction, see `## Root cause`).
- Unit boundary: a shared `_land_tidy` helper (Decision 6 below) is the one new named unit; the proof-and-guards block that decides whether to call it stays inline in `cmd_land`, used once, per the "if it needs a name and is used more than once, extract it" line this spec draws.

## Design

**Decision 1 -- the check runs AFTER today's `ahead == 0` refusal, and `ahead` moves to full refs.** The incident is a squash merge, and squash merges always leave `ahead > 0` (see `## Root cause`'s mutual-exclusion fact), so nothing about the incident needs the check to run any earlier. Running it before the `ahead` refusal was the first draft's approach; round 1 found it dangerous, because a freshly-created, zero-commit `wrap start` worktree is trivially an ancestor of `origin/<def>` (`_merge_proof`'s first route), and that ordering would have force-removed it (`worktree remove -f -f`, `:435`, which overrides the Agent tool's own lock) and deleted its branch -- destroying a live agent's ignored files and uncommitted work, and reversing the documented refusal at `docs/verification/wrap-land.md:3`. Round 2 found the mutual-exclusion argument that makes the corrected ordering safe depends on `ahead` and the ancestor check resolving the same refs, which they do not today (`ahead` uses short names; `_merge_proof` uses full refs, per its own tag-shadow comment). Two fixes, both applied: `ahead`'s command moves to full refs (`refs/remotes/origin/<def>..refs/heads/<branch>`), and the proof-handling code (TASK-3a) treats an ancestor-shaped proof string as equivalent to no proof at all, regardless of how it got that shape -- belt-and-suspenders, so a hole in the ref-resolution argument stays inert rather than dangerous. The fix stays scoped to the incident: after `ahead > 0` is already established via full refs, ask whether the ahead-looking commits are actually already landed.

**Decision 2 -- `tip` and `url` move above the branch point; `title`'s default computation does not move.** `tip` and `url` are declared at today's `:131-133` of `lib/wrap/wrap-land.sh`, after the `ahead` refusal, which is already above the new branch point (the proof call sits after the open-PR lookup, `:149-161`), so no move is needed in the modular code; the tail already reads `$url` at (today's) `:403` (the `base_open` lookup, `gh pr list --repo "$url" ...`) and `$tip` at `:407` (the origin-branch delete's `--force-with-lease=...:${tip}`). Once the new check can jump straight to the tidy tail without ever reaching `:131-133`, those two locals must already be set before that branch point, or the tail reads an unbound variable under `set -uo pipefail` (`lib/wrap/wrap.sh:84`). The origin-branch delete leases ONLY to this proven local `$tip` -- the SHA `cmd_land` itself verified, never a value later read back from origin. `title`'s default (`:134`, `_land_feature_title "$wt" "$def"`, only used when a fresh PR is actually opened) does NOT move: it stays in its current relative position and is computed unconditionally on both paths, which is harmless on the already-landed path (it goes unused there, since no PR is opened) and costs one cheap local `git log` read, no network.

**Decision 3 -- the dirty/tip recheck moves to immediately before the destructive removal, inside `_land_tidy`, on BOTH paths.** `_merge_proof`'s gh-squash route, and the freshness read in Decision 4, are both network round trips; time passes while they run. The first revision placed the dirty/tip recheck right after `_merge_proof` returned -- but Decision 4's freshness read, and `_land_tidy`'s own origin-branch-delete push and fast-forward pull, all still run AFTER that point and before the actual `worktree remove -f -f`/`branch -D` calls, so a recheck placed there is stale again by the time the destructive calls run. Round 2 asked to move it to directly before those calls instead, the way `_apply_worktrees` does at `:149-163` (its own recheck sits right before its dry-run gate, itself right before the removal a few lines later). This spec places the recheck inside `_land_tidy`, immediately before `worktree remove -f -f` and `branch -D`: it re-reads `git -C "$wt" status --porcelain` (must still be empty) and `git -C "$wt" rev-parse HEAD` (must still equal the `$tip` parameter). A mismatch reuses `_land_tidy`'s own existing `blocked=1` / exit-2 convention (today's `:421-431`, `:448`): it skips ONLY the worktree-remove and branch-delete calls and reports why, while whatever already ran (the origin-branch delete attempt, the fast-forward pull) stands as it is -- the same shape `_land_tidy` already uses for a blocked pull, extended to one more cause. Applying this uniformly to BOTH paths (not just the new short-circuit) closes a pre-existing gap in today's tail too: the existing merged-path tail has never rechecked dirty/tip before its own unconditional `-f -f` removal. The `git fetch origin "$def"` call itself (`:125`, its `rc` silenced today) is also checked (TASK-1): a failed fetch skips the new proof check entirely and falls back to today's unchanged path, since a fetch failure proves nothing either way.

**Decision 4 -- origin freshness, read ONCE, and it fails CLOSED.** A proof is about the LOCAL tip; it says nothing about whether origin's copy of `<branch>` has moved past that tip since the worktree last knew about it. Round 1 added a plain `ls-remote` read for this; round 2 found it fails OPEN: a bare `git ls-remote origin refs/heads/<branch>` prints nothing on a network or auth failure, identically to how it prints nothing when the ref is genuinely absent, so that failure read as "absent, proceed" -- the exact inversion of `_autoland_carry`'s own choice at `:82-83`, which treats an empty read as "cannot confirm" and REFUSES. The fix: `git -C "$wt" ls-remote --exit-code origin refs/heads/<branch>`. Its exit code is unambiguous: `2` means no matching ref (confirmed absent, proceed); `0` means a ref was found (compare the printed sha to the proven `$tip`: equal -> proceed; different -> refuse loudly by name, `origin/<branch> differs from the proven <tip>`, touching nothing, because pushed work would otherwise be reported "already landed" while it is not landed anywhere this run can see); anything else (network, auth, a transient git error) refuses by name too, exactly like a mismatch -- a failed read proves nothing, so it is never read as "safe to proceed." This read happens ONCE, before the "already landed" line ever prints, and its classification (`absent` or `present`, since a `differs` or a failed read already refused before this point) is passed into `_land_tidy` as an optional parameter (Decision 6's Interfaces) rather than read a second time there.

**Decision 5 -- a coexisting OPEN PR is reported, never silently resolved.** `_merge_proof` can return a proof (typically the absorbed route) while an open PR for this exact branch still exists -- either by coincidence, or by design: `wrap merge`'s `<branch>-squash` fallback (`commands/wrap.md:116`) commit-trees the merged tree onto a sibling branch and PR, and deliberately leaves the ORIGINAL PR for `<branch>` open for a manual close. When the (reused, not re-queried -- see Interfaces) open-PR lookup for this branch returns one or more results at the same time the proof holds, `cmd_land` reports BOTH facts on their own lines and refuses: no push, no PR opened, no origin-branch delete, no worktree or local-branch removal. This spec's own judgment call, since the decision above does not name the worktree's fate explicitly: leaving the worktree and local branch untouched too is the conservative reading of "leave ... untouched," and it keeps the operator's ability to inspect or close that PR from the same worktree.

**Decision 6 -- a shared `_land_tidy` helper; the Agent-lock guard is deliberately dropped, not shared.** The tail both paths need (the `base_open` guard and the origin-branch delete leased to `$tip`, `:397-415`; the fast-forward pull; the worktree removal; the branch delete; the existing exit-0-unless-blocked convention at `:448`; now also Decision 3's late recheck) is about 50 lines today (`:397-449`) and was going to be needed twice or duplicated. A named helper, `_land_tidy <repo> <wt> <branch> <def> <url> <tip> [<origin_probe>]`, replaces the inline block; both `cmd_land` paths call it once, at the end. **The origin-branch delete runs on the already-landed path too** (Interfaces, Picture and Task Breakdown all agree on this): a proven-landed branch is exactly the branch whose origin ref is safe to retire, leased to the tip `cmd_land` itself proved.

Round 1 also proposed reusing `_apply_worktrees`'s `_wt_lock_live` guard (`:85-90`) before trusting a proof, the same way `_apply_worktrees` uses it at `:161`. Round 2 asked to decide, explicitly, whether that guard is shared (in `_land_tidy`, both paths) or path-specific -- because `_apply_worktrees` and `cmd_land` are not the same situation. `_apply_worktrees` runs a batch sweep over worktrees OTHER than its own caller, so a live lock there always names someone else. `cmd_land <worktree>` has no such guarantee: its most common caller is the very agent whose lock the worktree carries, landing its own just-finished, just-merged work as its last step -- and the Agent tool's lock records that agent's own long-lived session pid, not any short-lived `wrap.sh` subprocess pid, so there is no reliable way for a bash script to tell "my own caller's lock" apart from "a genuinely different, still-live agent's lock" from inside itself. Checking the lock unconditionally, on either path, would deadlock the new short-circuit against the exact pattern it exists to serve (it can never see its own pid as dead while it is the one making the call). This spec's decision: **the lock is not checked at all**, on either path -- the existing merged path keeps forcing past it exactly as today (`:433`'s comment already documents this as intentional), and the new short-circuit does not add a check that cannot reliably distinguish self from other. The repositioned dirty/tip recheck (Decision 3) remains the operative protection against a worktree that is actively being written to at removal time, and it needs no pid at all. The residual gap -- a live agent that is momentarily idle (clean tree, unmoved tip) between writes gets its worktree removed anyway -- is named in `## Failure modes`, with the recovery: the branch's committed content is already proven landed, so nothing is lost there; the agent's very next tool call fails loudly ("no such file or directory") rather than silently, and the operator either lets the agent report the failure and stop, or hands it a fresh worktree to continue from if there is more work to do.

## Technical Design

### Interfaces (I/O contract)

- Consumes: `_merge_proof <repo> <def> <ghs> <branch>` (unchanged signature, no edit to the helper itself), called with `repo` (the main checkout, resolved at `:105-107`), matching `_apply_worktrees`'s exact call shape at `:146`. Also consumes a new `git ls-remote --exit-code origin refs/heads/<branch>` read (Decision 4).
- Produces: `_land_tidy <repo> <wt> <branch> <def> <url> <tip> [<origin_probe>]` (new). `<origin_probe>`, when given, is `absent` or `present` -- Decision 4's own classification, always one of these two by the time `_land_tidy` is reached on the already-landed path (a `differs` or a failed read already refused before that point). When omitted (the unchanged merge path, which never ran Decision 4's check), `_land_tidy` performs its own `ls-remote --exit-code` read for the SAME absence question, a read today's tail does not make (it attempts the delete and prints `FAILED delete` when the ref is already gone): only exit `2` means "gone," any other non-zero falls through to attempting the delete. Either way, `_land_tidy` also runs the existing `base_open` guard (`:397-415`, an open PR whose BASE is this branch blocks the delete, unchanged), leases the delete to the passed-in `$tip`, fast-forward-pulls the main checkout, re-checks dirty state and `$tip` one more time immediately before the final removal (Decision 3), then removes the worktree and deletes the local branch.
- Exit codes, stated completely rather than simplified: **0** on a clean land, either a genuine merge or the already-landed short-circuit, unless `_land_tidy` hits a blocked pull, a failed removal, or the new late recheck mismatch (all three already share `_land_tidy`'s existing `blocked=1` / `return 2` convention, `:448`); **1** on an early structural refusal (dirty worktree, no branch/detached HEAD, protected branch name, `gh` not ok, no commits ahead of `<def>`) -- unchanged from today; **2** on the open-PR-lookup/adopt/create family (unchanged in cause, though the lookup itself now runs earlier -- see below), a failed merge (state not `MERGED`), or one of this spec's new refusals (a stale dirty/tip mismatch caught right after `_merge_proof`, a `_wt_lock_live`-style check is NOT one of these, see Decision 6, an origin-freshness mismatch or unreadable `ls-remote`, or a coexisting open PR) -- all joining the existing "we looked something up and it disagrees" family by the same convention; **3** on a `MERGED` PR whose tree does not verify (`TREE MISMATCH` or unverifiable, `:355`/`:358`); git's own raw exit code on a `git push origin <branch>` refusal (`:138-142`, unchanged, only reachable on the no-proof path, since the proof-found path never pushes the branch's own content).
- **Intended behavior change, named explicitly:** the open-PR lookup moves from after the push (today, `:149-161`, which runs only once `ahead > 0` and the push already succeeded) to before it, run once and reused by both branches. A consequence: on the unchanged merge path, if the lookup itself fails, `land` now refuses with exit 2 BEFORE the branch is ever pushed, whereas today it pushes first and then fails the lookup, leaving a pushed branch behind with no PR to show for it. This is a deliberate improvement, not a side effect to route around.
- Invariant: the adopt path (`open_count -eq 1`) and the create-new-PR path (`open_count -eq 0`, no proof) are behaviorally unchanged in what they DO; only the branch that reaches them changes (a proven-landed branch with no coexisting open PR never reaches either now), and, per the point above, the open-PR lookup itself runs exactly once per `land` call, earlier than today, by design.

Two new stop-line shapes:

One new tidy-time refusal line for Decision 3's late recheck (`<branch> changed since it was checked; worktree and branch left in place`).

## Edge Cases

1. Branch has a `MERGED` PR into a DIFFERENT base than `<def>` (landed somewhere else): `_squash_verdict` returns `BASE <name>`, not `OK`, so `_merge_proof`'s squash route returns no proof; land falls through and opens a PR against `<def>` as today. Correct: a merge into another branch is not a merge into the default branch.
2. Branch's PR was closed WITHOUT merging (abandoned): no open PR, no merged PR (`_squash_json --state merged` never lists it), not absorbed. `_merge_proof` returns no proof; land opens a fresh PR, as it should -- an abandoned attempt is not a landed one.
3. `wrap.delete_merged_remote_branches` is `false`: `_land_tidy` still skips the origin-branch delete and reports it the same way on either path (`:400-401` today), unchanged.
4. The worktree is dirty when land runs: the existing dirty-check (`:112-114`) still refuses before any new code runs; unaffected.
5. **A zero-commit branch (`ahead == 0`) never reaches the new check at all**, by construction (Decision 1); it refuses exactly as today, and the ancestor route of `_merge_proof` is consequently unreachable from this call site in practice (see `## Root cause`'s mutual-exclusion fact and its full-refs fix).
6. **Known gap, not fixed by this spec:** a local tip STALE and BEHIND its own merged PR's recorded head (a GitHub "Update branch" click, a review-suggestion commit applied on GitHub, a bot commit -- anything pushed to the PR's branch on GitHub after the worktree's clone last fetched it, before the merge). `_absorbed` correctly fails (the local tip is missing content that IS on `origin/<def>`) and `_squash_verdict` correctly returns a `TIP <newer-sha>` mismatch (gh recorded a different, newer head as merged) -- so `_merge_proof` correctly reports no proof, and land's behavior is UNCHANGED by this spec: it falls through to today's path and opens a new PR for the branch's stale, incomplete content. Named here, and in `## After state`, because fetching only `origin/<def>` (`:125`) rather than the branch's own remote ref means land never learns the branch moved on GitHub's side.
7. `wrap merge`'s `<branch>-squash` fallback (`commands/wrap.md:116`) leaves the original PR for `<branch>` open while its content lands via a sibling branch/PR. `_merge_proof` has no dedicated check for this route (unlike `_autoland_carry`, which additionally checks `<branch>-squash`'s own merge record at `:86-90`); it is caught here only indirectly, when the sibling's commit-treed content happens to satisfy `_absorbed` for `<branch>`'s own paths. When it does, Decision 5's coexisting-open-PR report-and-refuse fires. When the sibling's tree diverges enough that `_absorbed` does not hold, `_merge_proof` returns no proof and land falls through to the unchanged path. Listed under `## Out of Scope`.
8. A worktree carrying a live Agent-tool lock, momentarily idle (clean tree, unmoved tip) between writes, whose branch is proven landed: the short-circuit tidies it exactly as an unlocked one (Decision 6). Its committed work is already proven landed, so nothing there is at risk; only uncommitted or ignored scratch could be lost, and the agent's next tool call fails loudly rather than silently.

| Decision 4's `ls-remote --exit-code` itself fails (any exit other than 0 or 2) | The `case` arm that is neither `2` nor a sha-comparable `0` | Refuses by name, fails CLOSED (TD3) -- the exact critical fix this round required, correcting a fail-OPEN bug in the prior draft |

| Origin already deleted the branch (squash-merge auto-delete), on either path | `ls-remote --exit-code origin refs/heads/<branch>` returns exactly 2, whether read via Decision 4's probe or `_land_tidy`'s own fallback read | Reports `already gone from origin` instead of attempting the delete (TD1, TB1) |
| A non-2 `ls-remote` failure inside `_land_tidy`'s OWN fallback read (the unchanged path only, no probe given) | Any non-zero, non-2 exit from that call | Never read as "gone"; the delete is still attempted and a real failure still reports `FAILED delete` (TB2) |
| PR closed without merging | `_squash_json --state merged` never lists a closed-unmerged PR | Already correct, no fix needed (Edge case 2) |
| A local tip stale and behind its own merged PR's recorded head | `_squash_verdict` returns `TIP <newer-sha>`; `_absorbed` also fails | Known gap, not fixed here (Edge case 6); land's behavior is unchanged from today (opens a new, incomplete PR) |
| Branch re-pushed with new commits after its earlier PR merged | `_squash_verdict` returns `TIP <old-sha>`, not `OK` | `_merge_proof` returns no proof; land opens a fresh PR for the new commits (TC4) |
| Fast-forward pull of the main checkout is blocked (dirty tracked file, wrong branch checked out) | `_land_ff_pull` returns non-zero, or `cur != def` | Unchanged from today: `PULL BLOCKED`, `_land_tidy` continues, worktree/branch removal still runs, exit 2 |

## Out of Scope

- Hardening `_squash_json`/`_squash_verdict`/the open-PR lookup's SILENT half to distinguish a failed `gh` call from a genuinely empty result (the open-PR lookup's own failure path is already loud and out of this concern; only `_squash_json`'s is silent). Shared by `_merge_proof`, `_apply_worktrees`, and `_autoland_carry`; changing its failure semantics is a separate, cross-cutting change.
- Giving `_merge_proof` (or land specifically) a dedicated check for `wrap merge`'s `<branch>-squash` fallback route, the way `_autoland_carry` layers one on top at `:86-90`. This spec catches that scenario only indirectly, through the absorbed route, and only when the sibling's content happens to satisfy it (Edge case 7).
- Fetching the branch's own remote ref (only `origin/<def>` is fetched, `:125`) to detect a local tip that has fallen behind its own PR's GitHub-side updates. Known gap, Edge case 6.
- A reliable way to distinguish "my own caller's Agent-tool lock" from "a different, still-live agent's lock" from inside a bash subprocess. This spec's answer is to drop the check entirely (Decision 6), not to attempt pid-ancestry matching, which the Agent tool's lock format does not support reliably at this layer.
- Recording a `ship` gate ledger line for the original PR (PR A in the incident) when `wrap land` takes the already-landed short-circuit. `/kit:ship` or an earlier `land` run already records that PR's ship gate on its own path; this spec does not add a new ledger-recording branch for a PR this run never opened.
- Any change to `_merge_proof`, `_absorbed`, `_squash_json`, or `_squash_verdict` themselves. This spec is `cmd_land` calling an existing, already-trusted check later and more carefully, not new proof logic.
- `feat/wrap-pull-only`'s own scope (`cmd_apply --pull-only`). See `## Siblings`.

## Decision Log

- DEC-1: Reuse `_merge_proof` rather than widening the open-PR lookup to `--state all` (Approach A) or narrowing to a gh-only check (Approach C). A rejected because it re-derives logic `_merge_proof` already gets right; C rejected because it needs every guard B needs for strictly less coverage (misses the absorbed route).
- DEC-2 (round-1 correction): the proof check runs AFTER the existing `ahead == 0` refusal, never before it, closing a lock-destruction risk the first draft's ordering opened.
- DEC-3 (round-2 correction): `ahead`'s own command moves to full refs, and a proof shaped like the ancestor route is defensively treated as no proof at this call site regardless, because the mutual-exclusion argument DEC-2 relies on only holds when both sides resolve the same refs.
- DEC-4: `tip` and `url` move above the branch point; `title`'s default stays where it is, computed unconditionally and harmlessly unused on the short-circuit path.
- DEC-5 (round-2 correction): the dirty/tip recheck moves from "right after `_merge_proof` returns" to "immediately before the destructive removal, inside `_land_tidy`," on BOTH paths, because every other network call this spec adds (the freshness read, the origin-branch delete, the fast-forward pull) still runs between the old position and the actual removal.
- DEC-6 (round-2 correction): the origin-freshness read uses `ls-remote --exit-code` and fails CLOSED on anything but a confirmed absence (exit 2) or a confirmed match (exit 0, sha equal), because a bare `ls-remote`'s empty output on a network failure is indistinguishable from a confirmed absence, and the first draft read it as the latter -- the inverse of `_autoland_carry`'s own choice on the same read.
- DEC-7: that freshness read runs once and its classification is passed into `_land_tidy` as an optional parameter, rather than read a second time inside the helper.
- DEC-8: a coexisting open PR for a proven-landed branch is reported and refused, never silently resolved one way or the other -- closing it could contradict `wrap merge`'s own documented `<branch>-squash` fallback behavior, which deliberately leaves that PR open for a human.
- DEC-9 (round-2 decision, explicitly delegated by the review): the Agent-tool lock guard round 1 proposed is DROPPED entirely, on both paths, rather than shared into `_land_tidy`. `cmd_land`'s most common caller is the very agent whose lock the worktree carries, and a bash subprocess cannot reliably tell that caller's own lock apart from a different agent's live lock, so checking it unconditionally would deadlock the short-circuit against its own primary use case. The repositioned dirty/tip recheck (DEC-5) remains the operative protection and needs no pid.
- DEC-10: the shared tidy tail is a named helper, `_land_tidy`, rather than duplicated code or one large conditional, because it is now called from two places with identical behavior, and its extraction (TASK-2a) is verified separately from its new behavior (TASK-2b) so a reviewer can trust the refactor did not itself change anything.
- DEC-11: the open-PR lookup moves earlier (before the push) on BOTH paths, an intended behavior change (not a side effect): a lookup failure now refuses before pushing rather than after, never leaving a pushed-but-unaccounted-for branch behind.
- DEC-12: a re-pushed-with-new-commits branch is deliberately left on today's unchanged path (no proof found), because `_merge_proof`'s existing tip comparison already resolves it correctly with no new special-case logic.
