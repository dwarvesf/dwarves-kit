## One module table and a smaller default install

### Context

`install.sh` kept `KIT_KNOWN_MODULES` and `kit_module_hooks()`. `lib/adopt.sh` kept a second copy that claimed to be in sync. It wired four modules, still knew the folded `bridge`, and lacked worktree, money_gate, prose_rag and sync. Drift row 43 and the "Consumer wiring gaps" risk. The plugin plus a bash install also double-fired every hook, and onboard only disclosed it.

### Decisions

- **Data file, not the registry.** The table is `lib/config/modules.tsv` (module, default, hooks as `Event:script`, CLIs), read through `lib/config/modules.sh`. `module-registry.md` stays the stage and env/key registry: it is markdown tables parsed by two other readers, and a hook-event column does not belong in its module-stage rows. The registry's `modules.*` default cells and `kit.toml [modules]` mirror the table's default column; `tests/test-modules-table.sh` pins both.
- **Events are checked, basenames drive the filter.** The install and adopt jq filters still match hook script basenames against `settings.json`, which owns matchers and command strings. The event column is verified by the test against `settings.json` and `hooks/hooks.json`, both ways, so a wrong event or an unwired hook fails a suite instead of drifting.
- **`spine` is a row, not a toggle.** Its hooks live in the table so every hook has one home, but `kit_modules_known` excludes it. It is never a valid `--with` name or a `[modules]` key.
- **Core means "on in a fresh install", not "always".** Core is `board`. A fresh install is one with no install record (`kit.toml` absent or a compat symlink) and no module hook already in `settings.json`. An existing install keeps its set; a re-run never adds the core set. `--prune` still trims to exactly `--with`. A per-project `.kit.toml` can turn `board` off, as before.
- **`--with` differs between the two scripts, on purpose.** `install.sh --with` is additive to the core set on a fresh install. `adopt --with` keeps its older meaning, the exact set, because `/kit:onboard` lets the user untoggle board and passes the final list.
- **Board is core, with a caveat.** Its hooks are `board-row-gate` (PreToolUse, already gated by `[gate] board_row_gate`) and `backlog-stage` on SessionEnd and, after slice S4, on SessionStart as `--surface` (that pass runs intake-sweep). Both stage entries are inert unless `BACKLOG_STAGE_AUTO=1`, and the sweep also needs `_meta/intake-sources.json`. The brief says intake-sweep is opt-in; it is opt-in by configuration, inside a core module, because a per-hook default column would cost a second axis in the table for one hook. intake-sweep.sh is not itself wired as an event, so the table lists `SessionStart:backlog-stage.sh`.
- **"Planes" and "audits" map to no module row.** The brief lists planes and audits as opt-in. Today queue, stats, worktree and sync (the plane-shaped modules) are all opt-in. The audit loops are commands and skills with no module toggle, so there was nothing to move.
- **Adopt wires nothing on a plugin machine.** The plugin's `hooks.json` registers every hook under a `${CLAUDE_PLUGIN_ROOT}` command string, which differs from the `$HOME/.claude/dwarves-kit/hooks/` string adopt writes, so adopt's per-project entries would double-fire next to the plugin. Adopt now asks the same detector, wires no per-repo hooks on `plugin` or `both`, and strips earlier kit entries from the project. This goes one step past the brief (it names install.sh) because the same double-fire lives in adopt. The committed project `settings.json` therefore depends on the mode of the machine that ran adopt; the plugin machine already registers all hooks, so nothing is lost there.
- **No user-level dedup in adopt.** A first draft skipped any hook the operator's own `~/.claude/settings.json` already ran, to avoid a double-fire after a default install wires board user-level. Claude Code runs an identical handler once across settings files (hooks reference: "If you define the same handler in more than one settings file, it runs once"; a plugin's copy of the same handler stays separate), so the skip bought nothing and made the committed file depend on which machine ran adopt. Dropped.
- **One detector.** `install.sh` asks `lib/onboard-detect.sh mode` and treats `plugin` or `both` as "refuse hooks". The old install check read the plugin cache glob for the compat branch and `installed_plugins.json` for the command step; they could disagree. The compat branch now also retires stale bare command links, because the roster-only case used to reach that code through the full path. The roster match tightened from any `dwarves-marketplace` entry to `kit@dwarves-marketplace`.
- **`--force-both` replaces `KIT_FORCE_FULL`, with the old spelling kept.** README, MANUAL and PHILOSOPHY outside this slice still name `KIT_FORCE_FULL=1`, so the env var stays as an alias in `install.sh` (one line, one test) until those docs move.
- **Retired hooks.** The table has no `session-state-save` and lists `backlog-stage.sh` at SessionStart, the end state of slice S4. Until S4 merges, `settings.json` still carries the first and lacks the second, so `tests/test-modules-table.sh` names both in two small exemption lists, and the additive-reinstall case in `tests/test-install-modules.sh` exempts the retired hook. Delete those lines when S4 lands.

### Not done

`hooks/hooks.json` (the plugin manifest) still registers every hook regardless of module choice. Module selection is a bash-install and adopt feature. Making the plugin follow the table needs a generated or per-module manifest, which is another slice.
