# tiered-verification: implementation notes

Spec: `docs/specs/SPEC-421-tiered-verification.md` (revision 3). Only deltas from the spec.

## Build delta

### Decisions and changes
- D1. The build worktree is `.claude/worktrees/tiered-verification-build`, made with a hand `git worktree add -b feat/tiered-verification`. `wrap start` refused: the spec branch's own worktree already holds `.claude/worktrees/tiered-verification`, and `wrap start` derives the directory from the branch slug. The branch name still gives the rid `tiered-verification`.
- D2. The golden is captured by `tests/lib/orchestrate-golden.sh` (dry-run plan plus `_wave_converge` console, events and hook argv for three cases) and committed before any `orchestrate.sh` edit. It pins config to an empty layer and `--board=roadmap`, so a later `kit.toml` default cannot move it.
- D3. The spec names no key for the join's full-suite command. Added `[test] join_cmd`, read at the base like the other test keys. With `verify = "tiered"` and no `join_cmd` the join refuses and nothing merges.
- D4. `classify` needs the run's exit code and the previous count, which the spec's signature omits. It takes `--exit <n>` (default non-zero, so a forgotten flag can never give `pass`), `--prev-count <n>` and `--known-from <file>`. "The last full run's count" is read as the executed count of the previous run of the same command in this node: an affected run never reaches a full run's count. The executed count is the sum of every numeric capture group of `count_line`.
- D5. The scripts gained verbs beyond `read`, `classify`, `guard`: `suite` (resolves the node scope: goal-file `Test-suite:` line, else `[test] suite` at the base), plus `names` and `count` for the join. `kit_config_get_at <repo> <rev> <key>` (base `.kit.toml`, then operator and kit-root, never the working tree) is new in `lib/config/kit-config.sh`.
- D6. Execute, verifier and ship steps are agent prompts, so C1 cannot count suite invocations in them. C1 asserts the resolver's output, that a branch edit of `.kit.toml` cannot move it, that resolving never runs the suite, and that all four step files name `known-failures.sh suite`. The two verifier agents cannot run the script (their Bash allowlist stays as it is): the lead resolves the scope, names it in their input, and runs `classify` on a red result.
- D7. The join treats the merged run as green when it exits non-zero only on failures in its own base run's set (`classify --known-from <base failure set> --prev-count <base count>`). The committed list is not consulted at the join, and a merged run whose count dropped below the base run's is red.
- D8. A moved head returns exit 75 from `mega-merge.sh merge`. `_wave_converge` reruns the join once for the sub-goals not yet merged, then stops the wave on a second refusal. The spec does not bound the rerun.
- D9. Serial path: not implemented. The spec says the serial path "joins per DAG level", but the serial loop never merges (each worker opens and merges its own PR), so a conductor join there would have no merge to gate and "DAG level" has no definition in the loop. Narrower reading: v1 joins on the wave path only. Open for the operator.
- D10. The rolling refusal fires on `WAVE_ROLLING=1` with `verify = "tiered"` whatever `WAVE_CAP` is, exit 64, before the dry-run plan and before any dispatch.
- D11. The known-failures file ignores blank lines and `#` comment lines. A `Known-failures: edit` declaration without a reason does not count. `failure_line` and `count_line` are TOML literal strings (single quotes, one layer stripped).
- D12. A goal file inside the repo is read as the base has it (`git show`), so a node cannot declare for itself; a goal file outside the repo is the lead's own file and is read directly. A goal file that is in the repo but absent at the base counts as no declaration.
- D13. The join reads each PR head with `gh pr view --json headRefOid` and, when the commit is not local, fetches `refs/pull/<n>/head`; an unreadable or unfetchable head stops the wave.
- D14. T5 (dotfiles skills) and T6 (Spacedown pilot, AC8) are not part of this build: they live in other repos and need a real run. Open for the operator.
- D15. C1 to C5 live in `tests/test-known-failures.sh`, C6 to C9 in `tests/test-orchestrate-tiered.sh`; the spec names those two files and does not split the cases. The fixture adds crash and baseline-red cases beside the nine.
- D16. One `kit:security-reviewer` pass ran on the build (not the full review-team). Fixed: a `--expect-head` with no usable value (empty, short, non-hex, trailing) now refuses with exit 64 instead of reading as "no expectation"; a join rerun re-resolves the base first, so it tests against the main the earlier merges moved.
- D17. Reviewed and not changed, open for the operator: (a) a node can edit the gate keys in `.kit.toml`, but `mega-merge.sh` already refuses any PR that touches `.kit.toml`, so a human merges it; (b) `classify` trusts `failure_line` to print every failure, so a failure in a format it does not match passes as known when another listed failure exists (needs a `fail_count_line`, a spec extension); (c) the join has no signal trap, runs `join_cmd` with the operator's full environment, and leaves `refs/kit/join-pr-N` refs; (d) a custom `WAVE_MERGE_CMD` that ignores `--expect-head` merges unjoined; (e) an unresolvable base ref reads `verify` as the kit-root default `off`.
- D18. Follow-up to D17(d): after the merge command returns 0 in a tiered wave, `_wave_converge` reads the PR head back (`gh pr view --json headRefOid`) and stops the wave, no merged event, when it is not the joined head. The hook is not trusted to have honored `--expect-head`. Test: C7 "ignores --expect-head".
- D19. Follow-up to D17(c): `_wave_join` traps INT and TERM for the length of the join. The handler stops the running suite, removes both throwaway worktrees, emits a `blocked` event for the wave and exits 130 or 143; the earlier traps come back after. The join command now runs in the background and is waited on so a signal is handled at once, with `KIT_CONFIG_*`, `KIT_PROJECT_ROOT`, `KIT_LEDGER_DIR`, `DWARVES_KIT_LOG_DIR` and `DWARVES_KIT` unset (`KIT_PROJECT_ROOT` and `DWARVES_KIT` added beside the named ones: they pick the same config and kit root). The `refs/kit/join-pr-N` refs are still left behind. Tests: C6 "scrubbed", C6 "interrupt".
- D20. Follow-up to D17(b): `classify --base-count <n>` makes `known` also require a count of at least the base run's, and a `--base-count` with no usable number is `fail` (not proven). The join always passes it, so a merged run with fewer executed checks than the base run is red even when every failure is known, and an unusable base count is red. A suite with no count line stays `fail`. A failure the `failure_line` regex never prints is still invisible when the count holds; that residue needs a failure-count line and is a spec extension.
