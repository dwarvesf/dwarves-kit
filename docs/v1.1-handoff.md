## Design philosophy (summary from docs/PHILOSOPHY.md)

Read the full PHILOSOPHY.md in the kit. Key principles:

1. **Guardrails over guidance** -- hooks (100% enforcement) over CLAUDE.md rules (70%)
2. **Synthesize, don't originate** -- every pattern traces to a source repo, no novel inventions
3. **One kit, whole cycle** -- .planning/SPEC.md is the shared contract across all commands
4. **Shallow and wide beats deep and narrow** -- 7 phases at 70% depth > 2 phases at 100%
5. **Bash over binaries** -- readable shell scripts, jq for JSON (one carve-out: HUD may use Node.js)
6. **External tools are dependencies, not features** -- check for Context Hub/Context7/codebase-memory-mcp, don't rebuild them
7. **Detect, don't dictate** -- suggest the right action based on state, never block workflow progression (except safety)

### Target user (updated in this session)
Two modes, one person:
- **Lead mode**: delegates to contractors, reviews PRs, plans features. Weekly cycle.
- **Coder mode**: builds directly with Claude Code 6-8 hours/day. Daily cycle. Needs HUD, faster approvals, slop detection, session persistence.

### Hard limits
- Maximum 35 files (currently 30)
- Maximum 500ms per hook
- No compiled binaries (except HUD carve-out)
- No paid dependencies
- No LLM API calls in v1 hooks

### Addition 1: HUD/statusline

**Source**: oh-my-claudecode HUD + Trail of Bits statusline.sh
**Why**: Coder mode needs context budget awareness. Without it, you don't know you're at 80% context until quality drops.
**What**: A statusline script registered in settings.json that shows: model name, git branch, context usage %, session cost, thinking mode on/off.
**How**: Bash script (or Node.js mjs if bash+jq is too slow for per-turn execution). Register in settings.json under `"statusLine"` field. Trail of Bits format: `[model] [branch] [X% used] [cost] [thinking: on/off]`
**File**: hooks/statusline.sh (or statusline.mjs)
**Settings.json**: Add `"statusLine": { "command": "bash $HOME/.claude/dwarves-kit/hooks/statusline.sh" }`

### Addition 2: ai-slop-cleaner (Stop hook)

**Source**: oh-my-claudecode code-simplifier
**Why**: After long sessions, Claude produces increasingly bloated code. A Stop hook that flags over-engineering catches this before it compounds.
**What**: Stop hook that checks recently modified source files for bloat signals: deeply nested callbacks (>3 levels), duplicated code blocks, functions >50 lines, unused imports, over-abstracted patterns. Does NOT auto-fix (that would need an agent hook). Instead, injects a context message: "These files may have unnecessary complexity: [list]. Consider simplifying before continuing."
**How**: Command-type Stop hook. Use git diff to find recently modified files. Grep for bloat patterns. If found, inject as additionalContext (not block). Must check stop_hook_active guard like anti-rationalization.
**File**: hooks/slop-cleaner.sh
**Settings.json**: Add to Stop event array (alongside anti-rationalization)

**Important**: This hook should NOT block (exit 0, not exit 2). It's a nudge, not a gate. The anti-rationalization hook blocks; this one suggests.

### Addition 3: Path-scoped rules template

**Source**: Claude-Code-Game-Studios .claude/rules/
**Why**: Dwarves projects are often polyglot (Go backend + TypeScript frontend). Different coding standards apply to different directories.
**What**: Create rules/ directory with 2 example files showing the pattern. Not enforced by hooks (Claude Code reads rules natively via path matching). Kit provides templates; user customizes.
**Files**: rules/backend-go.md, rules/frontend-ts.md
**Format**:
```markdown
---
paths: ["src/api/**", "pkg/**", "cmd/**"]
---
Use Go idioms. Error handling: return errors, don't panic.
Prefer stdlib over third-party libraries.
Test files go next to the code they test.
```

### Addition 4: Logging on all hooks

**Source**: disler/claude-code-hooks-mastery (structured logging pattern)
**Why**: Builds eval corpus passively. After 4 weeks, you have data to run AutoResearch optimization on hook patterns.
**What**: Every hook appends one line to its log file: `timestamp | event | outcome | project_dir`. Anti-rationalization already has this (added in v1.0). Extend to: safety-gate, context-readiness, spec-drift-guard, slop-cleaner.
**Where**: `~/.claude/dwarves-kit/logs/{hook-name}.log`
**Important**: Log on trigger only (when the hook actually does something), not on every invocation. A safety-gate log entry means a dangerous command was blocked. No entry means nothing interesting happened. This keeps logs useful.
